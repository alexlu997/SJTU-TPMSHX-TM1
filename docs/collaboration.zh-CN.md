# 协作与任务交接

[中文](collaboration.zh-CN.md) | [English](collaboration.md)

Codex、Claude 和 Antigravity 共用[项目规则](../AGENTS.md)、[运行说明](../README.md)和
[架构约定](architecture.zh-CN.md)。任务决定写入交接记录。聊天的私有上下文
不能代替交接记录。更换负责人或工具后，既有授权和未通过的验收条件继续有效。

Git 操作使用[任务持续授权](../AGENTS.md#1-task-scope-and-authority)。
每项任务仍遵守用户明确提出的范围限制。
对于宽泛目标，先调查并提出方向和验收条件，由用户确认方向后再实现。
方向确定后，自主完成约定工作、旧实现退役和必要验证，不逐步重复请求授权。

## 开始任务

1. 修改任务须明确唯一负责人、写入范围和协调者；任务需要审查时，还须明确审查方。用户未另行指定协调者时，
   负责人即协调者。每项独立修改任务使用一个
   工作树和一个分支，同一任务的后续工作复用它们。只读工作无需新建工作树。
   同一文件保持一个写入者。重任务使用[重任务名额](#重任务名额)。
2. 协调者检查主检出，将干净的 `main` 快进到 `origin/main`，并记录起点提交。遇到本地修改或
   历史分叉时，先保留并检查差异，再决定如何整合。
3. 从该提交建立任务分支。分支名体现代理，例如 `claude/<task>` 或 `neon/<task>`；
   用户或协调者另有指定时按其要求命名。在[任务状态](#任务状态)文件中登记工作树和分支。
4. 通过任务目录中忽略的 `.venv-path` 选择解释器。共享环境只承载依赖，位于任务
   工作树之外。适用锁文件一致时才能共用。环境相关工作开始前完成
   [环境检查](../AGENTS.md#3-work-setup-and-environment)。仅当解释器、依赖锁和已安装依赖均未改变时，
   才复用已通过的检查结果。环境相关故障后重新执行两项检查。
5. 项目源码从当前工作树导入。在工作树根目录使用 `python main.py` 启动应用。
   运行 Matplotlib、Qt 冒烟和 pytest 命令时，将 `MPLCONFIGDIR` 和 `XDG_CACHE_HOME` 设为本工作树忽略的 `.cache/` 路径。
   原生物性表缓存放在本工作树忽略的 `.cache/` 中。另行记录实际原生库及其源码和构建身份。检查是否仍引用待移除的工作树。

### 工作树准备

新工作树没有已发布的原生库，也可能没有 `.venv-path`：`.worktreeinclude` 只把该文件复制到 Codex 管理的工作树。

1. 若缺少 `.venv-path`，将其指向符合本任务依赖锁的已验收共享解释器。若已存在，按同一依赖锁核验。
2. 任务修改原生代码时，先构建并发布新库，再用其取证。
3. 任务不修改原生代码时，使用主检出中匹配的库，并按用途选择：
   - 几何、前处理和结果代码：设置 `TPMSHX_GEOMETRY_LIBRARY`、`TPMSHX_PREPARATION_LIBRARY` 和 `TPMSHX_RESULT_LIBRARY`。
   - 从 CLI 或 GUI 进行源码求解：传入 `--native-library` 和 `--native-table-directory`。
     在 Python 中，设置 `RunControl` 的 `native_library` 和 `native_table_directory`。
     `TPMSHX_NATIVE_SOLVER_LIBRARY` 不选择源码求解所用的求解库。
   - 使用 `tests/python/native/shared_library.py` 或直接读取该变量的原生测试：设置 `TPMSHX_NATIVE_SOLVER_LIBRARY`。
   - `tests/python/native/test_cpp_quick_design.py`：设置 `TPMSHX_SOLVER_LIBRARY`。
   - Linux x86_64 上的独立结果评估：仅设置 `TPMSHX_RESULT_LIBRARY`。
4. 不在工作树中为原生库目录添加符号链接。

## 多代理协作

协调者同时运行两个或更多任务人员时（例如 Orca 运行）适用本节。

1. 协调者将工作拆分为任务，为每个任务人员分配一项任务、一个工作树、一个分支和一个写入范围。
   各写入范围互不重叠。
2. 每个共享辅助文件、清单或测试支持文件只有一个负责人。原负责人交还后才可转交。
3. 本机同时最多五名活动实现人员。任务共享文件、相互依赖或等待审查时减少人数。
   审阅者和协调者不计入该人数。
4. 协调者负责以下事项：
   - 起点提交、写入范围和审阅者指派。
   - 重任务名额、合并队列和批量 PR。
   - `main` CI 失败后的修复和主检出更新。

   协调者不编辑任务人员写入范围内的文件。
5. 每份工单写明以下内容：
   - 目标、起点提交、工作树、分支和写入范围。
   - 依赖、已定限制和用户决定。
     对其他任务的每项依赖，写明上游任务、其负责人、已接受的上游合并提交，以及依赖它的下游测试节点。
   - [风险索引](agent-hazards.md)中与写入范围匹配的条目。
   - 适用依赖锁、原生库路径和检查。
   - 交付目标（已审查分支或自建 PR）、暂停条件和回报格式。
6. 任务人员需要修改写入范围外的文件时，先询问协调者。
   任务人员将需由用户决定的问题、阻塞、审查请求和结果发送给协调者。
7. 已授权运行中，任务人员与其协调者之间的消息无需另行批准。
   向其他聊天发送消息须获用户批准。
8. 依赖其他任务时，只有依赖它的下游节点的验收步骤需要等待，其他工作照常进行。
   下游分支纳入上游合并提交且依赖节点通过后才能交付。

### 重任务名额

重任务指原生构建、完整测试运行或重数值计算。
原生构建包括 `build_native_dependencies.py` 的 `build`、`publish` 和 `check-stages` 命令。
重数值计算包括求解、基准测试和字节比对运行。
按测试实际启动的工作判断其类别。启动原生求解或原生子进程的定向 pytest 文件属于重任务。
不启动重任务的定向 pytest 文件、`ruff`、`audit_import_graph`、`check_docs.py` 和[轻量推送前检查](#轻量推送前检查)
为轻量任务，可以并行。

1. 本机所有运行共用一个重任务名额，由一名协调者批准。名额自批准时起被占用，直到任务在启动前撤销该作业，或该作业及其子进程均已停止。
2. 重任务开始前，向协调者申请名额，获批后才启动。
3. 获批后，在状态文件中写 `Heavy job: approved`。
4. 作业启动时，改为 `Heavy job: yes`。
5. 作业完成或失败时，待计算及其全部子进程均已停止后改为 `Heavy job: no`，并向协调者报告结果：完成或失败。
6. 作业启动前撤销时，改为 `Heavy job: no`，名额立即释放，并告知协调者。
7. 取消运行中的作业时，保持 `Heavy job: yes`，直到计算及其全部子进程均已停止。
   然后改为 `Heavy job: no`，并告知协调者。
8. 每次批准前，协调者读取 `.cache/active-tasks/` 中的状态文件。
   另一文件显示 `Heavy job: approved` 或 `Heavy job: yes` 时，协调者不批准新作业。
9. 重启后，协调者查明当前名额持有人及其进程状态。

## 任务状态

任务状态文件向本机的其他任务、工具和后续会话说明当前工作。
它是本地文件，不提交；不在已提交文件中记录任务状态，也不把其中的本机路径复制到 PR。
任务名称为分支名，其中每个 `/` 替换为 `-`。
没有独立分支的任务使用一个简短名称，且不与其他状态文件重名。

1. 开始修改任务或重任务前，读取主检出 `.cache/active-tasks/` 中的每个文件。
   `git worktree list --porcelain` 的第一项是主检出。
   不写入其他有状态文件的任务的写入范围。另一状态文件显示 `Heavy job: approved` 或 `Heavy job: yes` 时，不启动重任务。
2. 修改任务开始时，在主检出中创建 `.cache/active-tasks/<task>.md`。
   没有状态文件的任务开始重任务时，也创建该文件。
   只有任务负责人写入该文件，唯一例外见第 6 步。
3. 在文件中写入以下各行：

   ```text
   Worktree: <absolute path>
   Branch: <branch, or none>
   Owner: <person or tool>
   Write scope: <files or directories>
   Heavy job: approved | yes | no
   State: active | blocked: <reason>
   Next action: <step and its owner>
   ```

4. 重任务开始或结束时更新该文件。任务暂停或继续、负责人或工具改变时也更新该文件。
5. 任务收尾时，先更新 PR 描述或交接记录，再删除该文件。批量交付的任务人员在协调者接收其分支后删除该文件。
6. 工作树缺失不能证明任务已结束。若文件所列工作树已不存在，协调者核对分支、PR、负责人和证据，
   并将结果告知用户。获用户批准后才删除该文件。
   若文件因其他原因看似过期，保留该文件并告知用户。

状态文件是当前写入者、写入范围、重任务、状态和下一步的唯一记录。任务收尾前，保持这些行最新。
创建、更新或删除状态文件时，无需进行存储占用测量。
缓存清理时，不删除其他任务的状态文件。

## 环境恢复

任务持续授权包含恢复已确定任务所需的环境，也包含在所需环境缺失时创建环境。
恢复依赖该环境的项目工作前，按以下步骤执行：

1. 说明故障、受影响任务、计划修改和恢复方法。记录适用锁、原解释器和指针、
   活动使用方。保留原环境及其源码版本。若不存在可用的旧环境，记录这一限制，
   并保留原有文件。
2. 使用适用的精确锁，在任务工作树之外的最终位置创建替代环境。
   可以用已安装且兼容的主机 Python 创建环境，记录其绝对路径和版本；
   该主机解释器只用于环境创建。安装和恢复检查使用替代环境的绝对解释器。
   这是恢复期间对活动 `.venv-path` 规则的明确例外。
   若没有适用解释器或所需访问权限，报告需要处理的具体事项。
3. 使用替代解释器执行锁检查和 `pip check`，从当前仓库根运行，使用工作树本地缓存。
   完成该环境用途所需的冒烟检查和预热。BO 和桌面打包环境分别使用自己的锁和验收检查。
4. 检查通过后，仅切换受影响且空闲任务的指针。活动使用方继续使用原环境，
   不修改或删除使用中的环境。通过新指针检查该任务；若失败，恢复原指针并保留失败记录。
   只有已验收的环境才能恢复项目执行。
5. 记录替代环境、检查结果、修改的指针和恢复路径。保留原环境，直到切换通过检查且
   原环境使用方为零。之后移除时仍须完成归档和清理检查。

恢复使用当前锁。依赖版本变更需要独立、范围明确的 PR，同时更新 `pyproject.toml`
和适用锁文件。切换前验证替代环境。

共享基础环境只安装 `engineering/requirements/base.txt` 中的依赖，不使用 `requirements.txt`。
其他环境用途使用各自的依赖锁。不以可编辑模式将本项目安装到共享环境。
锁检查不比较 pip 版本。其他项目 Python 进程使用共享环境时，不重建该环境。
修改共享环境会影响所有使用它的工作树。
日常启动器不安装依赖。服务器启动脚本使用预先配置的固定解释器，不安装或升级软件包。

## 关联修改记录

实现前追踪改动可达的使用方。
仅包含相关配置、保存文件、测试、夹具、导出、打包、示例、
GUI 和 CLI 标签、文档、注释和 docstring。
关联修改写在 PR 描述中。
契约指行为、接口、默认值、单位、限值、命令或文件格式。
契约改动须检查相关的现行文本，包括 Markdown、TXT 和其他相关文本文件。
改动不改变任何契约时，用一句话说明，不列出未修改项。
契约改动记录受影响的契约、更新内容、检查和未决事项。
写明覆盖某一使用方的检查名称。只有将该使用方与改变后的契约进行比较的检查，才算覆盖该使用方。
只固定字面标签的测试不覆盖单位改动。
仅当理由不明显或没有检查覆盖时，才说明未修改使用方的理由。理由相同的使用方合写一句。
交付前完成必要更新。审阅者从需求和差异追踪使用方，再与此记录核对。

## 旧代码完整退役

替换或删除任务在实现前记录待退役代码；替换任务还须记录新行为。PR 创建前，该记录保存在工单或与协调者的消息中，
之后写入 PR 描述。详细本地证据保存在忽略的 `.cache/` 中。

1. 追踪公开和内部调用方、动态名称、CLI 和 GUI 入口和外部使用方，覆盖配置、当前版本的保存文件读取器、
   导出、打包、测试、夹具和文档。核对实际使用关系；`legacy`、`old` 等名称、文件名或搜索无命中都不足以证明可删除。
2. 按当前使用方需要的行为检查替代实现，保留物理、数据和平台要求，同时测试当前版本的保存和读取。
   C++ 数值执行和 Python 应用接口仍属于当前产品能力。
3. 在同一 PR 中迁移使用方和回归覆盖，删除被替代实现及其专属文件。
   同步更新入口、构建清单、配置、导出和文档。保留有效回归覆盖，历史源码使用 Git 保存，
   不在工作目录保留重复的备份文件。
4. 核对残留引用并运行相关使用方和回归检查。每个保留项记录使用方、原因和明确删除条件。
   退役未完成时，分别报告实现与退役状态；任务要求的退役和验证全部通过后才能完成任务。

实现任务中发现的范围外缺陷连同证据先记录，交付后按持续授权另开 PR 修复。
每个后续 PR 覆盖一项此类缺陷及其必要后果。明确要求只读的任务继续保持只读。

探索代码在现有任务记录中写明研究问题、成功标准和采用或退役条件。
只有明确的产品、研究或独立参照用途才能支持其留在主线。
记录使用方和再次评估条件，退役前保存必要结论和未提交证据。
当前结果保持单位、模型与算法身份及版本、指标定义和有效性状态可读。
读取需求的改变不授权移除仍受支持的续算或执行接口。
产品或算法改变须先给出证据、选项和推荐，再由用户确定方向。

## 测试范围

新增或修改回归测试时遵守以下规则：

1. 只添加改动所需的测试，即覆盖本次新增或改变的有意义行为，或本次修复的已证实失效。
   现有检查能覆盖该行为或失效时，使用现有检查；没有检查覆盖时，补充最小测试。
   优先使用少量映射检查；保留能区分独立失效条件的必要组合。不添加重复现有检查的测试。更新受本次改动影响的现有测试。
2. 通过转换边界校验后，不再重复组合 `dtype` 或选项。
   在转换边界测试转换，并保留代表性的端到端算例。
3. 仅当测试实际读取临时文件时，才写入临时 JSON、NPZ 或 HDF5 文件。
   C ABI 布局和指针测试写在 `tests/cpp/*_c_smoke.c` 中，不把公开适配层复制为 `ctypes` 镜像测试。
4. 不测试离屏像素坐标、固定边距值或内部 mock 调用次数，也不为已删除符号添加 `ModuleNotFoundError` 测试。
   不添加防御性测试。例如，不为被测程序不可能进入的状态写测试。
   测试状态变化、物理要求、资源清理和已文档化的契约。

## 同步与审查

第 1–4 步由负责人完成；第 5–8 步的合并顺序由协调者确定。
用户未另行指定协调者时，负责人即协调者。

1. 完成相关检查，仅提交任务范围内的修改。提交内容不含本地数据、环境和探索报告。
   按[工作树准备](#工作树准备)指定原生库。在干净且已提交的任务树上运行[轻量推送前检查](#轻量推送前检查)，
   审查前和首次推送前必须通过。用文本搜索或导入图找出每个已改模块的直接导入方。
   运行 `tests/python` 下所有导入该模块的测试文件。
   运行其他导入方的测试、改动的定向测试和 `tests/python/architecture/test_three_module_imports.py`。
   检查未选中这些测试或将其记为待验重任务时也要运行。这类测试启动重任务时，使用[重任务名额](#重任务名额)。
   记录这些测试及其结果。
2. 无需用户提醒，主动对待审提交启动所需的[独立审查](#独立审查)。
   只修正文档错字、链接或格式的 PR 无需审查；它不得改变任何规则、命令或契约的含义，
   且 `engineering/scripts/check_docs.py` 必须通过。在 PR 中写明这一理由。
   完成修订，每次增加提交后更新审查结论。
   记录实际审查方，不把代理审查写成人工独立批准。
3. 推送任务分支，创建或更新 PR，将[交付记录](#交接记录)写入 PR 描述。PR 中不写本机绝对路径。
   [批量交付](#批量交付)时，将已审查分支、证据和关联修改记录交给协调者，不自建 PR。
   此后由协调者负责批量 PR 描述、CI、合并和 `main` CI。
4. 等待最新 PR 提交的必需 CI。依据持续授权修复任务相关失败，重跑受影响检查，
   并更新审查结论。范围外的未解决失败须记录下一步处理动作。
   审查通过后，CI 修复同时满足以下全部条件时，无需新的审查轮次：
   - 只修改 `tests/` 下已有的测试文件，不修改生产代码。
   - 自获批提交起，全部修复提交的新增与删除行数合计不超过 10 行。按 `git diff --numstat` 将每个修复提交与其第一父提交比较后相加。
     `origin/main` 的合并不计入。
   - 不删除检查，不减弱断言，不修改容差或契约值，不添加 `skip` 或 `xfail`。
   - 协调者按以上条件核对差异。PR 中记录该核对结果、统计行数、获批提交、修复提交和失败的检查。
   - 修复提交的[轻量推送前检查](#轻量推送前检查)通过。
   - 修复提交的必需 PR CI 全部通过。
   批量 PR 的获批提交是协调者在批量交付第 3 步比对过的批量分支提交。
   其他修复按常规审查轮次处理。
5. 等待协调者通知轮到合并。新提交到达时，`main` CI 会取消正在运行的任务，
   仓库保护又要求分支为最新，因此一次只合并一个 PR。仅当没有正在运行的 `main` CI 时开始合并。
6. 将当前 `origin/main` 合入任务分支并解决冲突。保留分支历史，不强推或覆盖其他负责人的改动。
   将任务差异与已审查差异加上第 4 步已接受的修复比对。仅当合并无冲突、任务补丁与之完全相同且相关行为和契约均未改变时，
   才无需新的审查轮次。否则，对受影响的路径进行小范围审查。重跑受影响检查。等待必需的 PR CI。
7. 必需审查、测试、CI 和仓库保护条件全部满足后，以合并提交方式合并，不绕过仓库保护。
8. 等待合并后 `main` 提交的必需 CI，并在 PR 评论中写明合并提交和 `main` CI 结果。
   CI 通过后，由协调者将干净的主检出快进至已验收提交，然后才能开始下一次合并。

必需的 `main` CI 失败时，保留失败记录。协调者重跑可恢复的失败。需要修改代码时，修复 PR 获得下一个合并位。
修复通过 `main` CI 前，暂停无关合并。

PR CI、合并后主线 CI、桌面验收和实验验证分别记录结论。

### 轻量推送前检查

`engineering/scripts/pre_push_check.py` 按改动路径选择轻量检查。
选测基准为 `origin/main` 与 `HEAD` 的合并基准。其他基准引用用 `--base` 指定。
`--head` 必须指向干净且已检出的提交。

1. 提交全部改动。工作树有未提交或未跟踪的文件时，检查停止。
2. 在仓库根目录运行 `"$(head -n 1 .venv-path)" -m engineering.scripts.pre_push_check`。
3. 阅读 `.cache/pre-push/<head>.txt` 中的运行记录，将其摘要行写入审查请求和 PR 描述。

检查对每个差异运行 `check_docs.py`。对不属于 `docs` 层级的差异，还运行以下项目：

- 依赖锁检查、`pip check`、对改动 Python 文件运行 `ruff`，以及 `darwin` 和 `win32` 的 `check_types`。
- `audit_import_graph --fail-on-violations`，其中包括导入环检查。
- 改动测试文件和映射使用方中已核实为轻任务的节点，使用 `-m "not slow and not heavy"`。
  检查中的轻任务核实名单列出这些文件和节点。

运行记录为每个必需节点给出一个结果：通过、失败、跳过、未收集、待验重任务或待 CI 验证。跳过不算通过。
检查与 CI 一样设置 `TPMSHX_REQUIRE_NATIVE_DEPS_TESTS=1`，因此缺少原生库或调用程序记为失败。
待验重任务节点不在轻任务核实名单中，或带有 `slow` 或 `heavy` 标记。按第 1 步运行，或由 PR CI 关闭。
依赖锁检查或 `pip check` 失败时，停止其他检查，并写出失败记录。
待 CI 验证项写明关闭它的 CI 作业，合并前由同一 head 的 PR CI 关闭。
记录还列出没有映射使用方的已改模块，按第 1 步追踪其导入方。
“轻量检查通过”和“全部必需检查通过”是两个不同的结论。

只有核对调用链后，才能把使用方节点或轻任务文件加入检查。
该调用链不得启动原生求解或长时间运行的子进程，允许短时 Git 元数据查询。
检查会输出[风险索引](agent-hazards.md)中与改动路径匹配的条目。

Git 钩子 `engineering/hooks/pre-push` 接受与推送提交和同一选测基准相符的完整通过记录。
钩子按推送目标判断，检查每个分支更新。
没有这样的记录时，若工作树干净且位于推送提交，钩子运行检查；否则停止推送。钩子忽略标签和分支删除。
协调者执行一次 `git config core.hooksPath engineering/hooks`，关联工作树共用该设置。
未经协调者批准，不使用 `git push --no-verify`，并在 PR 中记录原因。

### 批量交付

协调者可以将多个已审查分支放在一个 PR 中交付，只运行一套 CI。

1. 从当前 `origin/main` 建立批量分支。
2. 每个已审查分支以各自的合并提交并入。
3. 将每个合并提交的第一父提交差异与其已审查差异比对。
4. 冲突修正改变已审查的行时，对这些行进行小范围审查。
5. 运行受合并改动影响的集成检查。
6. 创建一个 PR，用表格列出每个分支的基准、已审查提交、审阅模型、轮数、检查和结论，
   并附上各分支的关联修改记录。
7. 按合并流程第 4–8 步交付该批量 PR。

### 独立审查

负责人提供需求、基准与待审提交和证据。
Orca 运行中，由协调者以独立的只读任务人员身份启动审阅者。
审阅者未参与实现，也不继承作者聊天记录。
规则不会创建文件监视器或技术门禁。审阅者只读是角色职责，不代表操作系统隔离。

按以下规则选择审阅者：

- 改动涉及物理含义、数值结果、单位、文件格式、公开接口与 C ABI、平台行为或项目规则时，
  使用与作者不同的模型审查。
- 其他工作使用排队较短的独立审阅者。该审阅者可以与作者模型相同，但须使用新上下文。
- 架构方案和代理规则改动使用两名不同模型的审阅者。
- 需要不同模型审查时，使用以下默认配对：Neon 审 Astra，Astra 审 Neon，Astra 或 Neon 审 Opus。
  Astra 为 Codex 模型，Neon 为 Antigravity Gemini 模型，Opus 为 Claude 模型。
  默认模型不可用时，记录原因，再换用与作者模型不同且能覆盖相同范围的其他独立模型。

1. 向审阅者提供需求、已接受约束、工作树、基准与待审提交、适用规则和测试证据。
   包含作者的关联修改记录、轻量推送前检查的摘要及相关既有决定。审阅者返回前，保持被审工作树不变。
2. 审阅者先从需求和差异独立追踪关联使用方，再与作者的关联修改记录核对。
   审阅者核对推送前运行记录属于待审提交，没有失败、跳过或未收集的必需节点。
   记录遗漏使用方时，由作者补充该使用方的证据。
   阅读相关代码和模型文档，包括动态入口和保存文件使用方，不限于作者的文件清单。
3. 检查关联修改遗漏、无必要代码、重复规则、多余抽象和退役不完整。
   正确性单独检查，包括物理要求、数据、当前使用方和证据覆盖。
   代码相似不足以支持共享。保留必要复制、物理校验、独立测试参照和有用参照实现。
4. 每条阻止意见提供稳定编号、位置、可达使用方或维护场景、后果和最小改法。
   说明适用的已有证据或最少需要补充的检查。不规定发现数量；风格偏好和无证据猜测不阻止交付。
   首次发现的历史问题不自动属于本次改动。将其列为阻止项前，说明它与当前交付或既有验收的直接关系。
5. 负责人修复意见，或提供保留代码的依据。审阅者核对针对阻止意见的反证。
   非阻止建议需要处理结论，但不单独触发复审。审阅者不编辑文件或写入 Git。
   必要检查由负责人按现有环境和资源规则执行。证据有疑点时，负责人做针对性复验。
6. 初次实质审查和后续每次实质复审各计一轮。原审阅者可用时，修正由其继续复审。
   更换审阅者或拆分 PR 时保留原意见和累计轮数。两名审阅者审查同一提交范围时，两份报告合计一轮，
   各自记录结论。第三轮后仍有阻止意见时，无需用户批准即开始第四轮。第四轮只审查为解决这些意见而做的改动。
   第四轮后仍有未决意见时，向用户提交未决意见、提交范围、证据、选项和最小改法。
   第五轮及以后各轮须由用户针对指定意见和提交范围明确批准。
7. 后续提交、同步 `main` 或解决冲突时，更新覆盖记录。
   无冲突、任务补丁与已审查补丁加上[交付流程](#同步与审查)第 4 步已接受的修复相同，且相关行为和契约未改变的同步，
   只需比对差异，不占一轮。其他同步对受影响路径复审。
   不无故重复全量审查。复用有效测试证据，没有具体需要不重复重数值计算。
   工具不可用或必要证据缺失时保持审查未完成。不把作者自查写成独立审查。

记录审查提交、审阅模型、轮数、未决意见、证据和结论。
正确性报告为“未发现阻止问题／存在阻止问题／检查未完成”之一。未发现问题不证明代码没有缺陷。
交付结论为“可进入后续检查／需修正／需用户决策／审查未完成”。
具体阻止项和必要证据决定该结论。
轮数上限不豁免物理、数据、平台或 CI 要求。实现不得通过降低自身审查要求来取得通过。

## 交接记录

每类记录只有一个所有者：

| 记录 | 内容 |
| --- | --- |
| [任务状态](#任务状态)文件 | 当前写入者、写入范围、重任务、状态和下一步 |
| PR 描述 | 交付记录 |
| `.cache/<task>/HANDOFF.md` | 本机证据、本机路径和阻塞 |

PR 描述包含以下内容：

- 改动及其[关联修改记录](#关联修改记录)。
- 检查及对应提交，包括轻量推送前检查的摘要。
- 审查结论、审阅模型、审查提交和轮数，或无需审查的理由。
- PR CI 结果。
- 未通过的验收条件。

合并后，在 PR 评论中写明合并提交和 `main` CI 结果。

符合以下任一条件时，在 PR 描述中加入表中全部字段：

- 任务跨越多个 PR 或会话。
- 任务因阻塞暂停。
- 负责人或工具改变。
- 退役未完成。

| 字段 | 必填内容 |
| --- | --- |
| 任务 | 目标、写入范围、授权范围 |
| 人员或工具 | 负责人、审查方、协调者 |
| 代码 | 起点提交、分支、当前提交、审查提交、PR |
| 关联修改 | 受影响的契约和使用方；更新内容和覆盖检查；理由不明显或未经检查的未修改使用方的理由；退役范围和保留理由 |
| 审查 | 审阅模型与上下文方式、提交覆盖、意见与处理、轮数和结论 |
| 运行条件 | 适用锁、环境用途、原生构建、数据版本 |
| 证据 | 检查项目、对应提交、结果、本地证据记录名称 |
| 状态 | 已完成内容、失败项、未通过的门槛、待批准事项 |

本地私有记录包含工作树、解释器、原生库、数据链接目标、证据路径、受阻交接和未完成退役。
仅当任务有本地证据或阻塞时，建立该记录。位置为任务工作树中的
`.cache/<task>/HANDOFF.md`，其中 `<task>` 使用[任务名称](#任务状态)。
保留原始失败和未运行状态。共享记录以记录名称引用私有证据。
接手方先读共享记录和状态文件，再核对本机路径，然后执行命令。
PR 创建前需要由另一台机器继续任务时，使用指定的 issue 承载共享交接。

## 归档与清理

移除工作树前，确认所属任务、写入者和运行进程、未提交或未推送内容、运行资源
使用方及 ignored 证据。在移除范围之外保存必要提交和本地材料，记录原路径、提交、
锁文件、成员清单和链接目标。归档工作树时不跟随原始数据链接。

逐文件比对归档与原件。各恢复一份代表性报告、输入文件和输出文件，逐一读取。现存缺失或
格式损坏单独记录，不改变历史结论。同盘归档不算独立备份；应用的 Git 快照不能
代替 ignored 证据归档。

上述检查通过且活动使用方为零后，才能移除工作树或环境。使用其所属应用或对应的
Git 工作树管理操作。最后处理分支，先确认必要提交有恢复入口。旧筛选结果只归档，
不恢复已退役的求解或优化链；当前多工况 BO 继续作为独立能力维护。

## 存储保留原则

任务向 TM1 缓存写入数据或清理缓存前、任务收尾时和已授权的存储清理期间，均遵守以下规则。目录名为 `.cache/` 不代表其中科研证据可以直接删除。
`git worktree list --porcelain` 的第一项是主检出。`.agents/rules/tm1-local-data.md` 中的相对路径以主检出为起点。

常规工具缓存写入前无需测量。这些缓存指 `MPLCONFIGDIR` 和 `XDG_CACHE_HOME` 路径、pytest 缓存和状态文件。
本机设有缓存上限时，在向 TM1 缓存写入其他数据前和清理前测量合计分配占用。
范围包括主检出和各工作树的 `.cache/`，以及上限涵盖的其他 TM1 缓存。同一硬链接文件在这些位置只计一次。符号链接只计自身占用。
每个写入过 `.cache/` 的任务在收尾时测量一次，每次清理结束时也测量一次。
每次测量前，先列出当时纳入上限的全部缓存位置，再测量其合计分配占用；即使没有删除文件也要测量。

1. 保留原始数据、正在使用的论文与 GCI 证据、选中设计和关键失败样本，以及对应输入、方法、最终场、指标和适用限制。
   保留研究的全部参数、种子、标量观测、约束和原始结论。清理不能把已停止、已否决或未开始的工作改成成功。
2. 中间场和检查点须有明确的分析或续算用途。已结束的软件测试和性能研究不默认永久保留续算状态。
   记录移除的字段、检查点及不再可用的恢复操作。未完成工作保留至所属任务负责人决定其状态。
3. 临时输出可以指定位置时，放在本任务的工作树中。
   检查通过后，列出本任务的一次性脚本、测试输出、构建产物和可重建缓存，并在交接前删除。
   批量删除这些文件时，使用用户已批准的确切清单。
   保留其他任务、应用程序或留存研究仍需使用的文件。
   保留解释或复现科研证据所需的研究脚本。归档只包含本任务的必要文件，禁止递归归档整个 `.cache/` 或其他任务归档。
   已提交源码从 Git 恢复；大型记录可以无损压缩。
4. 每种活跃用途只保留一个已验收环境：基础、BO、最小后处理。打包或历史环境须注明使用方和删除条件。
   新环境验证、指针检查及零活动使用方确认通过后，退役旧环境。先保存准确包版本、源码版本、依赖锁和独有本地文件。
5. 文件系统属性允许时，共享内容相同的固定快照；保留已保存的相对路径，硬链接不可用时保留独立副本。
   禁止将可变构建输出直接硬链接到证据目录。更新共享文件须整体原子替换，禁止原地覆盖内容。
   移除来源前检查保留结果和代表性恢复路径。
6. 在任务交接记录中说明保留内容、使用方以及删除或复查条件。报告新增、删除、剩余目录占用和卷可用空间的实测变化。
   如果合计占用仍超过本机上限，在同一份交接记录中写明超出量和下一步。
   未经用户批准，只能删除明确列出的可重建缓存和本任务自身的临时文件。删除科研内容须经用户批准，即使只有一个文件。
   任何批量删除（包括可重建缓存和本任务临时文件）须有用户已批准的确切清单，不能仅按日期或目录名判断。

## 工具规则入口

Codex、Claude 和 Antigravity 共用 `AGENTS.md` 中的项目规则。
[Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 和 Antigravity
直接读取工作树根目录的 `AGENTS.md`。Antigravity 只在主检出中运行时读取 `.agents/rules/` 中的本地规则。
链接工作树中没有这些被忽略的文件；在链接工作树中，按 `AGENTS.md` 第 2 节查找本地数据规则。
[Claude Code](https://code.claude.com/docs/en/memory#agentsmd) 读取已跟踪的根目录 `CLAUDE.md`，
该文件用 `@AGENTS.md` 引用项目规则。不要依赖 Claude Code 对 AGENTS 的直接支持。
默认模式下，它在项目或上层目录发现 `CLAUDE.md` 时会跳过 `AGENTS.md`。检出位于用户主目录下、
`~/.claude/CLAUDE.md` 存在且 `CLAUDE_CONFIG_DIR` 指向其他目录（例如 Orca 配置目录）时会出现这种情况：
Claude 会把 `~/.claude/CLAUDE.md` 当作上层目录文件。
首次接入时在实际客户端检查规则加载。规则只保存在 `AGENTS.md` 中，不复制到 `CLAUDE.md` 或第二套规则。
